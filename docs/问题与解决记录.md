# 问题与解决记录（面试弹药库）

> 规则来源：AGENTS.md 工程规范。凡"现象 ≠ 预期"的问题，解决当天必须入档。
> 每条含四要素：**现象 / 根因 / 解决 / 面试一句话**。★ = 面试高价值，建议主动讲。

---

## A. 环境与工具链

### P1 ★ PEP 735 依赖组的"假成功"（2026-09-16）

- **现象**：`pip install -e ".[dev]"` 显示成功，`pytest` 却报 No module named pytest。
- **根因**：pyproject 用了 PEP 735 `[dependency-groups]`，本机 pip 24.0 不支持该标准，**静默忽略**主依赖组之外的内容——安装"成功"是假的。
- **解决**：改用经典的 `[project.optional-dependencies]`，所有 pip 版本都认 `.[dev]`；在 pyproject 注释里写明原因。
- **面试一句话**："新标准被旧工具静默忽略会造成假成功——我对'装上了'保持怀疑，用冒烟测试验证环境，而不是相信安装日志。"

### P2 Docker Hub 直连被墙，pgvector 镜像拉不下来（2026-09-16）

- **现象**：`docker pull pgvector/pgvector` 报 dial tcp 超时。
- **根因**：registry-1.docker.io 在当前网络不可达；本机代理（技能默认端口）也未运行。
- **解决**：国内镜像源前缀拉取再 retag：`docker pull docker.m.daocloud.io/pgvector/pgvector:pg16` → `docker tag` 回官方名；不动 Docker 配置、不重启。
- **面试一句话**："环境受限时的原则是改拉取路径而不是改系统配置——retag 后一切按官方镜像使用，方案可复制给任何被墙的镜像。"

### P3 editable 安装失败：包结构未声明（2026-09-16）

- **现象**：`pip install -e .` 报 flat-layout 多顶层目录发现失败。
- **根因**：backend/ 下的包没有 `__init__.py`，pyproject 也没有 packages 声明。
- **解决**：补六个 `__init__.py` + `[tool.setuptools] package-dir/packages` 显式声明。
- **面试一句话**："包不可 import 的问题要在第一天用声明式配置解决，而不是靠 sys.path 补丁到处打。"

## B. 模型与推理

### P4 ★★ 本地模型加载挂死 18 分钟（2026-09-17）

- **现象**：入库脚本加载已下载好的 BGE-M3，无报错、无输出，挂死 18 分钟。
- **根因**：transformers/huggingface_hub 在加载时**默认联网检查模型更新**，huggingface.co 被墙 → 每个 HTTP 请求都等超时重试，表现为"无声挂死"。
- **解决**：本地加载一律加 `HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1`（权重已在本地缓存，无需联网）；首次下载用 `HF_ENDPOINT=hf-mirror.com`。
- **面试一句话**："最难缠的 bug 是无声挂死——我用排除法定位到'加载即联网'这个隐式行为，并把离线 flag 固化成团队约定。排查工具的隐式网络行为是被墙环境的基本功。"

### P5 嵌入模型选型与维度契约（2026-09-16）

- **现象**：embedding 列该开多少维？模型输出 float64 也直接入库吗？
- **根因/决策**：BGE-M3 输出 1024 维 → `vector(1024)` 定长（HNSW 建索引的前提 + 类型即安检）；模型默认 float64，统一转 float32（精度损失可忽略、存储减半）。
- **面试一句话**："向量维度是模型与库之间的契约，定长写进 schema；float32 是向量工程惯例。"

## C. 数据库与存储

### P6 ★ PG 全文检索不支持中文——BM25 通路瘫痪（2026-09-17）

- **现象**：tsvector 建好了，中文查询却几乎无命中。
- **根因**：PostgreSQL 内置分词器不认识中文，**一整句被当成一个词**，倒排索引形同虚设。
- **解决**：入库时 jieba 先切词存 `tokens` 列，`tsv` 做成从 tokens 计算的**生成列**；查询端用同一 jieba 切法。选型上排除 zhparser/pg_jieba（需编译扩展，Windows 容器装不了）——jieba 纯 Python 零编译是该约束下的唯一解。
- **面试一句话**："两端必须同套分词——入库切'上限值'、查询切'上限 值'，倒排索引就查空；分词器是一致性契约，不只是预处理。"

### P7 ★★ 幂等设计：自增主键挡不住重复数据（2026-09-17）

- **现象**：语料重灌一遍的需求，暴露主键选型问题。
- **根因**：若用自增 `SERIAL` 主键，重灌产生全量重复行——向量检索 top-5 被同一张卡占两席，**挤出真正相关的条款 → 漏检**。
- **解决**：chunk_id 三段式业务主键（`{standard_id}:{clause_no}:{sub_idx}`）+ `ON CONFLICT DO NOTHING`；实测重跑处理 46、新增 0、总数仍 46。
- **面试一句话**："幂等不写在 if 里，写在唯一键里——自增主键挡重复插入这个行为，挡不住重复数据本身。"

### P8 外键顺序：先登记标准再挂卡片（2026-09-17）

- **现象**：chunks.standard_id REFERENCES standards——插入顺序错误时全部被拒。
- **解决**：ingest 流程固定"先 standards 后 chunks"。
- **面试一句话**："外键是数据库替你做的引用完整性检查；顺序约束靠流程注释+测试固化。"

## D. 代码缺陷（被测试/评测当场抓住）

### P9 ★ tsquery 保留符号：'1:3' 的冒号炸掉整条查询（2026-09-17）

- **现象**：评测一首跑，qid2 "绘图能用1:3的比例吗？" 直接语法报错崩溃。
- **根因**：jieba 把"1:3"切成 "1"、":"、"3"，**冒号是 tsquery 语法的保留操作符**，`to_tsquery` 直接语法错误。手工演示的查询词干净，永远测不出这种边界——**评测集的价值当场兑现**。
- **解决**：正则白名单 `_TSQUERY_SAFE`（字母/数字/下划线/中文）过滤查询词，全被剔除时短路返回空。
- **面试一句话**："演示用的干净查询测不出系统边界——评测集跑第一遍就抓到一个手工演示永远遇不到的崩溃，这正是'评测集先于调参'纪律的回报。"

### P10 缺 import 的两种死法（2026-09-16/17）

- **现象**：chunking.py 用了 `re` 没导入（自查发现，当时无测试覆盖）；retrieve.py 用了 `register_vector` 没导入（运行当场炸）。
- **根因**：分段追加代码时 import 区没同步。
- **解决**：当场补 + 如实记录；后续靠"每段写完立即运行对应测试"约束。
- **面试一句话**："没被测试覆盖的路径，错了都没人知道——这两个 import 一个靠自查一个靠运行炸，差别就是有没有测试在场。"

### P11 ★ 测试断言与夹具不一致（2026-09-17）

- **现象**：rrf 单测失败，报错差值 0.00026。
- **根因**：断言抄了教材数字（第1名+第2名 = 1/61+1/62），夹具却写的是两路均第 1 名（应为 2/61）——差值恰好 1/61−1/62。
- **解决**：断言对齐夹具。
- **面试一句话**："测试红了先别怀疑产品代码——断言、夹具、产品三方要对账，那次差值精确等于两个预期之差，一眼锁定是测试自己的账。"

## E. 设计权衡与简化（面试主动讲的"我知道简化在哪"）

### P12 ★★ 语料条款引用与编号的"位置漂移"（2026-09-16）

- **现象**：'4.2.1' 的树地址（chapters[3].sections[1]）取决于"前言是否入树"的约定——约定变，位置漂。
- **解决**：解析器固定"前言不入树"，**查找永远按 clause_no 不按位置**——条款号是唯一不漂移的地址，也是 chunk 主键与引用溯源锚点。
- **面试一句话**："位置会随约定漂移，编号不会——整个系统的主键体系建立在'永不漂移'的那个维度上。"

### P13 结构化分块 vs 现成切分器（2026-09-16）

- **现象**：LangChain 递归字符切分会腰斩条款、合并短条款、切碎表格。
- **根因**：证据门控要求"引用原文必须是某卡片文本的子串 + 条款号真实存在"，这要求 **chunk 与条款约 1:1**——固定长度切分在数学上就不满足。
- **解决**：自研结构化分块（章→节→条树，叶子条款=卡片；超 800 字按句子边界零宽断言拆分，标点保留，守恒断言 `拼接==原文` 钉死"拆而不丢"）。
- **面试一句话**："不用现成 splitter 不是重复造轮子——证据门控的可行性建立在 chunk↔条款 1:1 上，这是通用切分器给不了的结构性质。"

### P14 ★ 切分必须保标点：一个正则连着证据门控（2026-09-17）

- **现象**：超长条款拆分若用普通 split，句号被当分隔符吃掉。
- **根因**：吃标点后卡片文本**不再是原文的精确子串** → 门控第 2 查误杀正常结论 → 全变 B 级拒答。
- **解决**：零宽断言 `re.split(r"(?<=[。；])")` 在标点后的"空隙"切，字符守恒断言防回归。
- **面试一句话**："一个切分正则的正确性标准不是'看起来分得对'，而是'拼接后与原文逐字相等'——因为它直接决定下游子串校验的生死。"

### P15 ★ ts_rank 是简化版 BM25：简化明示（2026-09-17）

- **现象**：BM25 通路用 PG 的 ts_rank 实现，但它**没有语料级 IDF**、长度归一默认关闭。
- **决策**：v1 接受简化（倒排匹配保召回、rerank 管精排），严格版（手动 IDF 或专用扩展）列为 v2。
- **面试一句话**："我知道自己的 BM25 是简版、简化在哪、代价是什么（下文的实测负结果就是代价的证据）——知道简化在哪比假装没简化值钱。"

## F. 评测与负结果（面试金矿区）

### P16 ★★ 评测一负结果：混合检索反而低于纯向量（2026-09-17）

- **现象**：recall@5 纯向量 1.00 → 混合 0.98 → +rerank 1.00（n=50）。教科书说混合必胜，我们的数据说不。
- **归因**（三因）：①46 卡小库，纯向量已饱和（1.0 无提升空间）；②ts_rank 无 IDF，"配合"这类高频词的字面票被高估；③candidate_k=20 给单路字面票留了挤占机会。
- **BadCase 实录**：唯一 miss 是 qid50"电气标识检查不合格允不允许出厂"——gold 6.1 被**三份标准的 6.2 条款群**集体挤占；且 6.2 本身也是合理命中（gold 标注存在边界模糊），如实记录不粉饰。
- **修复与收益**：rerank 把混合的 0.98 修回 1.00；同时给出现场证据——重排把海选第 5 的真相关条款拉到第 2（0.92）、混入的无关条款识破（0.25），**相关度悬崖**（0.99/0.92/0.25/0.06）成为 M2 B 级拒答的天然阈值钩子。
- **面试一句话**："我最重要的检索数字不是 1.00，而是那个 0.98——负结果+归因证明评测体系真的在测量，而不是在证明。"

### P17 ★ rerank 延迟：CPU 上 7 秒/查（2026-09-17）

- **现象**：50 条评测里 rerank 档平均延迟 7.05s，另两档 0.1s 级。
- **根因**：cross-encoder 对 20~40 个候选逐对全交互，CPU 算力受限。
- **决策**：如实记录；生产路径=GPU 推理或砍 candidate_k；评测口径保持一致不偷改。
- **面试一句话**："精度提升有价格标签——我把它标出来（7s/查），让部署决策者选，而不是假装没成本。"

### P18 术语条款解析不了的显式边界（2026-09-16）

- **现象**：第 3 章 `**3.1　术语名**` 格式与条款正则不匹配，v1 未入库。
- **决策**：v1 明示边界（评测集不设 3.x 题），v2 专门处理。
- **面试一句话**："解析器的覆盖边界写进文档和评测集，不写进沉默的丢数据。"
