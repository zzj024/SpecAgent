## 已能讲清单

### 0. 项目一句话（对外口径）

工程标准符合性审查多智能体：五 agent 流水线（路由→检索→审查→校验→报告），
每个结论强制挂「条文原文+条款号+置信度」证据链，证据不足分级拒答不硬答；
pgvector+BM25 混合检索加重排，LangGraph 编排可断点续跑，七套评测数字支撑。

### 1. 环境（2026-09-16）

- **一句话价值**：一套 PostgreSQL 同时解决向量、全文检索、业务表，少一个组件。
- **数据流**：FastAPI → psycopg3 → Docker 里的 pgvector/pgvector:pg16 → HNSW 索引。
- **为什么 pgvector 不用 Chroma/FAISS**：Chroma/FAISS 停留在"demo 级"——没处理过
  分片、ANN 调优（m/ef_construction/ef_search）、持久化运维；pgvector 与业务表同库，
  条款号 join、全文检索、事务都是 SQL，M3 的 checkpointer 也复用 PG。
- **为什么条款号是天然主键**：入库时是结构化分块的切分单位与去重键；
  出报告时是证据三元组的溯源锚点、校验 Agent 程序化核对的对象。

### 2. 语料设计（2026-09-16）

- **一句话价值**：自写模拟标准 + 公开元数据，版权安全且结构可控，是分块/检索/评测的共同输入。
- **数据流**：corpus/*.md（章→节→条结构，含表格/图占位/跨标准引用/长度悬殊四个刻意难点）
  → 未来 rag.parse → chunks 表。
- **为什么埋难点**：真实标准本来就有表格和跨引用，语料必须逼真；且难点先入语料
  = 提前定好对照实验，评测一跑完 BadCase 能归因（"表格被切碎→改分块→数字提升"）。
- **为什么三份选机械/焊接/电气**：按测试目的选——机械与电气差异大测路由分流，
  焊接与机械有交集测多意图与检索边界。不是顺手写。
