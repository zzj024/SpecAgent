## 已能讲清单

### 0. 项目一句话（对外口径）

工程标准符合性审查多智能体：五 agent 流水线（路由→检索→审查→校验→报告），
每个结论强制挂「条文原文+条款号+置信度」证据链，证据不足分级拒答不硬答；
pgvector+BM25 混合检索加重排，LangGraph 编排可断点续跑，七套评测数字支撑。

### 1. 环境（2026-09-16）

- **一句话价值**：一套 PostgreSQL 同时解决向量、全文检索、业务表，少一个组件。
- **数据流**：FastAPI → psycopg3 → Docker 里的 pgvector/pgvector:pg16 → HNSW 索引。
- **为什么 pgvector 不用 Chroma/FAISS**：Chroma/FAISS 停留在"demo 级"——没处理过
  分片、ANN 调优（m/ef_construction/ef_search）、持久化运维；pgvector 与业务表同库，
  条款号 join、全文检索、事务都是 SQL，M3 的 checkpointer 也复用 PG。
- **为什么条款号是天然主键**：入库时是结构化分块的切分单位与去重键；
  出报告时是证据三元组的溯源锚点、校验 Agent 程序化核对的对象。

### 2. 语料设计（2026-09-16）

- **一句话价值**：自写模拟标准 + 公开元数据，版权安全且结构可控，是分块/检索/评测的共同输入。
- **数据流**：corpus/*.md（章→节→条结构，含表格/图占位/跨标准引用/长度悬殊四个刻意难点）
  → 未来 rag.parse → chunks 表。
- **为什么埋难点**：真实标准本来就有表格和跨引用，语料必须逼真；且难点先入语料
  = 提前定好对照实验，评测一跑完 BadCase 能归因（"表格被切碎→改分块→数字提升"）。
- **为什么三份选机械/焊接/电气**：按测试目的选——机械与电气差异大测路由分流，
  焊接与机械有交集测多意图与检索边界。不是顺手写。

### 3. RAG 基础与证据门控（2026-09-16，三轮复述过关）

- **一句话价值**：RAG = 先查后答、照原文答，结论才挂得上"依据 X 条"；
  证据门控让这个"依据"不可能造假。
- **数据流**：文件 → 解析成目录树（章→节→条）→ 叶子条款 = 卡片(chunk)，
  引用句记进 refs（口诀：谁引用记谁）→ 向量化入库 → 检索 → 审查 → 三查 → 报告。
- **为什么按条款切**：chunk↔条款 1:1，"依据"才指得准、子串校验才成立；
  超长条款拆分后条款号=组地址、sub_idx=页码，核对时查整组。
- **三样检查（面试原题级）**：①条款号真实存在（代码查库）→ ②引用文本确为
  原文子串（代码比对）→ ③证据支持结论（独立 LLM 判定）。
  分工原则：前两样是事实核对零幻觉，第三样是推理核对只能靠模型——
  先代码后模型，能用代码的绝不交给模型。
- **为什么记忆深刻**：三轮复述，第 3 查（证据支持结论）连丢两次，
  最终靠"术语定义撑不起不符合"的反例应用题过关。

### 4. 向量检索原理（2026-09-16，复述过关）

- **一句话价值**：把"按意思找"变成"按距离找"，解决关键词匹配对不上口语表达的问题。
- **数据流**：卡片文字 → BGE-M3 → 1024 维坐标点；问题也变点 → 找最近 k 张
  （pgvector `<=>` 距离排序，HNSW 索引=小世界社交网络跳跃加速）。
- **核心性质（必背原句）**："意思相近的文字，坐标点挨得近"——
  同义不同字的 query 能命中全靠这一条（首答只说"按语义搜"是循环论证，
  被纠正后补上性质本身）。
- **两个为什么**：为什么 pgvector——向量+全文+业务表一个 PostgreSQL 全包；
  为什么 recall@5 用 5 不用 1——正确条文进前 5 候选圈即可，后面有 rerank 补救排名。
- **边界（引出下周课）**：向量不擅长精确匹配（条款号、标准号）→ 双通路混合检索。
